1. What it stores

Per participant, per day: food items (library id, label, quantity, unit, estimated energy and macronutrients); medicine name, dose and the day's status (taken / skipped / changed); systolic, diastolic, pulse, glucose and context, weight, energy, mood, sleep, a free-text note; and a timestamp.

Profile: participant code, age-band code, condition codes, medicine list, consent version and timestamp, a random device ID and creation time. Settings: language, reminder on/off and time, PIN hash and salt, optional sync URL, last sync status and a "hide previews" flag.

None of this is a name, phone number, address or government identifier. See the privacy notice for how it is used.

2. Encryption at rest

  • Algorithm: AES-256-GCM, 128-bit tag, random 96-bit IV per record.
  • Key: generated inside AndroidKeyStore under alias khai_record_key_v1, non-exportable, setUserAuthenticationRequired(false) so background sync works while the screen is off.
  • Associated data: code|date. Moving a ciphertext row to another participant or date makes decryption fail.
  • Storage: a SQLite table entries(code, date, iv, ct, updated_ms, dirty). There is no plaintext column.
  • Erase: rows are deleted and the Keystore alias is deleted, so residual bytes are undecryptable.
Threat-model consequence: this protects the database file, a stolen powered-off phone, a backup and forensic extraction of app storage. It does not protect against an attacker who can run code as the app's user on an unlocked device, because the app can obtain the key. The PIN is an interface gate, not a second key.

3. Device protections relied upon

  • Android file-based encryption for the whole device.
  • App sandbox — /data/data/in.khaifoods.tracker is not readable by other apps.
  • android:allowBackup="false", with extraction rules excluding database, prefs, files and external storage from cloud backup and device transfer.
  • FLAG_SECURE when "hide previews" is on, stopping recent-app thumbnails and screenshots.
  • HTTPS-only network security config; cleartext is disabled at the manifest and the config.

4. The PIN

Four digits, salted, PBKDF2-HMAC-SHA1, 120 000 iterations, 256-bit output, constant-time compare. Re-locks after 60 seconds in the background. Removing it requires access to the unlocked app — the same trust boundary.

A four-digit PIN has 10 000 possibilities, so the hash is a speed bump, not a defence against offline brute force if the salt and hash leak. Its real job is to keep a family member or a borrower out of the interface. PIN is not two-factor authentication and does not add cryptographic protection.

5. Network and sync

Sync is opt-in and requires an https:// base URL. It retries once on transport failure, does not follow redirects and rejects non-2xx responses without retry on 4xx. The payload is a full upsert of all local days for one participant: {code, device_id, days: {date: entry}}. The contract is POST {base}/api/sync.

The browser demo has no sync at all — nothing leaves the browser. In the app, sync is off by default.

Known gaps before production: no certificate pinning; no per-device authentication token (the server must add one and the app must send it); no request signing or replay protection beyond idempotent upsert; the participant code is the only subject identifier, so server-side authorisation must be strict; and sync runs on a background thread with no visible progress or backoff schedule.

6. Exports and sharing

Files are written to the app's private cache and exposed through a non-exported ContentProvider with a one-shot read grant on the share intent. The provider rejects path traversal in file names and serves only existing cache files.

Exported files are plaintext by design — they are meant to be read by a clinician. The participant chooses the destination app; Khai does not upload them. The cache is not cleared automatically, so export cache expiry is a pre-production task.

7. Logging and third parties

No analytics, crash reporting, advertising or attribution libraries are linked. There are no Log.* calls in the shipped source; exceptions are caught and ignored rather than printed with record content. The only network endpoint is the study server the participant configures. There is one optional, inexact daily reminder whose notification text contains no clinical values.

8. Build and supply chain

The APK is built by tools/build.py from locally installed JDK 17, Android SDK 35, Kotlin 2.0.21 and bundletool.jar. Release signing uses a 4096-bit RSA key. No dependency manager is used, so there is no transitive dependency surface. tools/check.py is the release gate and the build is reproducible without Gradle or an IDE.

Development key. The keystore currently in the repository is a generated development key, not a production signing identity. Replace it and enrol in Play App Signing before any real distribution. This APK is a technical preview, not a Play Store release.

9. Verify the APK

The downloadable file is signed and hashed. Compare before installing:

File:     khai-tracker-1.0.0.apk
Package:  in.khaifoods.tracker
Version:  1.0.0 (versionCode 1)
SHA-256:  505778d284882d5568c745ffb9382fb59f0e675c0b17592ba6c512a4ba29e31a

On Windows PowerShell:

Get-FileHash .\khai-tracker-1.0.0.apk -Algorithm SHA256

On macOS or Linux:

shasum -a 256 khai-tracker-1.0.0.apk

The machine-readable value is in files/khai-tracker-1.0.0.apk.sha256. Verify the signing certificate too: apksigner verify --print-certs khai-tracker-1.0.0.apk (from Android build tools). The build gate confirmed v2 and v3 signatures, v1 false, RSA 4096, subject CN=Khai Foods Pvt Ltd. A mismatch means the file is not the one built here — do not install it.

10. Pre-production checklist

  • Replace the development keystore; enrol Play App Signing; store the upload key in a vault.
  • Add server authentication and per-device credentials; document key rotation.
  • Decide on certificate pinning with a documented rotation plan.
  • Add export cache expiry, and a job-scheduler sync with backoff and progress.
  • Add a privacy-preserving crash reporter or explicitly accept its absence.
  • Run a DPIA and a penetration test on the phone + server pair.
  • Confirm the legal basis and consent text per jurisdiction.
  • Set real, monitored privacy and security mailboxes.
  • Execute the app on physical devices across Android 7–15 and record the results.

11. Reporting a vulnerability

Email security@khaifoods.in with the build version, device and Android version, steps to reproduce and the impact. Please do not include participant data. We aim to acknowledge within seven days. Until the mailbox is monitored before public launch, treat this as a disclosure process to establish, not a live SLA.
