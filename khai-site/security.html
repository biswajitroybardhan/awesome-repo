1. What it stores

Per participant, per day: food items (library id, label, quantity, unit, estimated energy and macronutrients); medicine name, dose and the day's status (taken / skipped / changed); systolic, diastolic, pulse, glucose and context, weight, energy, mood, sleep, a free-text note; and a timestamp.

Profile: participant code, age-band code, condition codes, medicine list, consent version and timestamp, a random device ID and creation time — all encrypted with the same Keystore key. Settings: language, reminder on/off and time, PIN hash/salt and failure count, optional sync URL, per-device token, optional SPKI pin, explicit sync consent, last sync status and a "hide previews" flag that is on by default.

None of this is a name, phone number, address or government identifier. See the privacy notice for how it is used.

2. Encryption at rest

  • Algorithm: AES-256-GCM, 128-bit tag, random 96-bit IV per record.
  • Key: generated inside AndroidKeyStore under alias khai_record_key_v1, non-exportable, setUserAuthenticationRequired(false) so background sync works while the screen is off.
  • Associated data: code|date. Moving a ciphertext row to another participant or date makes decryption fail.
  • Storage: a SQLite table entries(code, date, iv, ct, updated_ms, dirty). There is no plaintext column.
  • Profile: conditions, medicines, age band and consent metadata are encrypted with the same Keystore-backed key under AAD khai-profile-v1. Only non-sensitive settings stay in SharedPreferences.
  • Erase: rows, encrypted profile, settings and the Keystore alias are deleted, so residual bytes are undecryptable. Generated export files are deleted too.
Threat-model consequence: this protects the database file, a stolen powered-off phone, a backup and forensic extraction of app storage. It does not protect against an attacker who can run code as the app's user on an unlocked device, because the app can obtain the key. The PIN is an interface gate, not a second key.

3. Device protections relied upon

  • Android file-based encryption for the whole device.
  • App sandbox — /data/data/in.khaifoods.tracker is not readable by other apps.
  • android:allowBackup="false", with extraction rules excluding database, prefs, files and external storage from cloud backup and device transfer.
  • FLAG_SECURE is on by default when "hide previews" is left untouched, stopping recent-app thumbnails and screenshots. A participant can turn it off knowingly.
  • HTTPS-only network security config; cleartext is disabled at the manifest and the config.

4. The PIN

Four digits, salted, PBKDF2-HMAC-SHA1, 120 000 iterations, 256-bit output, constant-time compare. Re-locks after 60 seconds in the background. Failed attempts now trigger exponential backoff from 5 seconds up to 5 minutes, and the gate is disabled while the wait runs. Removing it requires access to the unlocked app — the same trust boundary.

A four-digit PIN has 10 000 possibilities, so the hash is a speed bump, not a defence against offline brute force if the salt and hash leak. Its real job is to keep a family member or a borrower out of the interface. PIN is not two-factor authentication and does not add cryptographic protection.

5. Network, sync and analysis

Sync is off until an institution address, a per-device bearer token and explicit consent are configured in Settings. The app accepts an absolute https:// URL only, rejects embedded credentials, query strings and fragments, never follows redirects, and retries once on transport failure. It sends only days still marked unsynced: {schema, code, device_id, days: {date: entry}} to POST {base}/api/sync.

An optional SPKI pin (base64 SHA-256 of the server public key) adds certificate pinning on top of system trust anchors. A 2xx response is not sufficient: the server must return accepted_dates, and the app clears the unsynced flag only for dates confirmed in that response.

The browser demo has no sync at all — nothing leaves the browser. The app has no ads, advertising identifier or third-party analytics SDK. Institution staff may analyse trends only in records synced under the recorded consent, under a signed data-processing agreement; no automated care decisions are made from them.

Still required before real data: a named institution endpoint, token issue/revocation, a documented pin-rotation path, strict server-side authorisation per participant code, retention and erasure controls, a DPIA and a penetration test. The app cannot make a server secure; the server contract is recorded in khai-tracker-android/docs/SECURE_SYNC.md.

6. Exports and sharing

Files are written to the app's private cache and exposed through a non-exported ContentProvider with a one-shot read grant on the share intent. Every provider method validates the filename and serves only existing regular cache files.

Exported files are plaintext by design — they are meant to be read by a clinician. The participant chooses the destination app; Khai does not upload them. CSV cells that begin with a spreadsheet formula character are prefixed with an apostrophe, so a free-text note cannot become a formula when staff open the file. Files older than 24 hours are removed when a new export is written, and “Erase my data” deletes the whole export cache.

7. Logging and third parties

No third-party analytics, crash reporting, advertising or attribution libraries are linked. Institution-side trend analysis runs on the server under consent, not in an SDK on the phone. There are no Log.* calls in the shipped source; exceptions are caught and ignored rather than printed with record content. The only network endpoint is the institution server the participant configures. There is one optional, inexact daily reminder whose notification text contains no clinical values.

8. Build and supply chain

The APK is built by tools/build.py from locally installed JDK 17, Android SDK 35, Kotlin 2.0.21 and a SHA-256-pinned bundletool.jar. Release signing uses the dedicated 4096-bit RSA upload key held outside the repository. Signing passwords are read from a user-only file or environment; the build redacts them from output, passes them to apksigner through an environment variable and gives bundletool only a short-lived password file. No dependency manager is used, so there is no transitive dependency surface. tools/check.py asserts the security controls and tools/verify.py checks the artefacts.

Upload key, not a Store listing. This APK is signed by the dedicated upload key and is a technical preview. Enrol in Play App Signing before distribution; Google will then hold the app signing key that users actually trust.

9. Verify the APK

The downloadable file is signed and hashed. Compare before installing:

File:     khai-tracker-1.0.0.apk
Package:  in.khaifoods.tracker
Version:  1.0.0 (versionCode 1)
Size:     1,284,457 bytes
SHA-256:  40803ec96f6068ffe4dc863f7a429e496db33fa42c7424e9110e377d1c693b4f

On Windows PowerShell:

Get-FileHash .\khai-tracker-1.0.0.apk -Algorithm SHA256

On macOS or Linux:

shasum -a 256 khai-tracker-1.0.0.apk

The machine-readable value is in files/khai-tracker-1.0.0.apk.sha256. Verify the signing certificate too: apksigner verify --print-certs khai-tracker-1.0.0.apk (from Android build tools). The build gate confirmed v2 and v3 signatures, v1 false, RSA 4096, subject CN=Khai Foods Pvt Ltd, OU=Khai Tracker upload, certificate SHA-256 20531590f7adf747957e69b87f5a82a3e318252f038ba91c01d7fb07bb95105b. A mismatch means the file is not the one built here — do not install it. Publish the Play app-signing fingerprint through an independent channel once Console issues it.

10. Pre-production checklist

  • Enrol Play App Signing; back up the upload key in a team vault; publish the Play signing fingerprint out of band.
  • Provision the institution endpoint, issue and revoke per-device tokens, and test token rotation.
  • Publish the SPKI pin with a documented rotation plan and test a refused wrong-certificate connection.
  • Test full, partial and missing accepted_dates responses; add job-scheduler sync with backoff and visible progress.
  • Decide explicitly whether a privacy-preserving crash reporter is wanted; none is shipped today.
  • Run a DPIA and a penetration test on the phone + server pair.
  • Confirm the legal basis, clinic licence and consent text per jurisdiction.
  • Set real, monitored privacy and security mailboxes.
  • Execute the app on physical devices across Android 7–15 and record the results.

11. Reporting a vulnerability

Email security@khaifoods.in with the build version, device and Android version, steps to reproduce and the impact. Please do not include participant data. We aim to acknowledge within seven days. Until the mailbox is monitored before public launch, treat this as a disclosure process to establish, not a live SLA.
