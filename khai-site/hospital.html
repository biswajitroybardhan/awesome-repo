Hospital deployment · reference design

The hospital is the unit of change.

A phone record only closes a loop when a clinic can act on it. This page is a reference architecture for that hospital layer — roles, queues, reconciliation, integration, audit and governance. It is a design blueprint: nothing here is deployed, no hospital is named as a partner, and the labelled illustration in the browser demo uses synthetic data only.

1. Status of this document

Shipped Demo Roadmap

Shipped is the participant app and exports in 1.0.0. Demo is the labelled hospital control-room illustration in the browser demo; it uses a synthetic cohort, stores only local demo objects, and has no hospital connection. Roadmap is every hospital-side component below: each one needs a partner, a governed environment and a named clinical owner before it can exist. The pattern is described generically; no individual or institution is presented as associated with Khai.

Read this as a blueprint, not an announcement: no hospital deployment, pilot, endorsement or partnership is claimed. The intended first context is a public-hospital setting in India; that is a direction, not an existing site.

2. Why the hospital, not just the phone

An offline-first participant instrument solves the measurement gap: food, medicine status and home readings between visits. It cannot, by itself, close the loop. A measurement that nobody reviews is a data graveyard; a flag that nobody owns is an alarm; a draft that nobody signs is not a plan. The loop only closes when a named clinician receives the record, acts on it, and the action is auditable.

That is why the hospital layer is the real unit of change. The phone is the Capture node; the hospital is where Verify, Review, Medication, Follow-up and Operate happen. Building those nodes as a reference design — with explicit roles, queues and governance — lets a real site adopt one loop rather than buy a dashboard nobody opens.

6. Clinician review workflow

The clinician artefact stays one page. It separates what was measured, what was missed and what is only self-reported; it shows flags as prompts, never as triage decisions; and it exposes the reasoning behind any plan draft so the clinician can disagree with the basis, not just the conclusion.

  • Review pack: completeness, recent readings, medicine status, food frequency and notes — generated from the record, not typed by hand.
  • Flags with source days: each flag links to the days that produced it, so the clinician can inspect the evidence before acting.
  • Draft with visible reasoning: every point states the counts and averages behind it. Accept, Edit and Reject are recorded with an author and a timestamp.
  • Override review: a monthly sample of overrides is reviewed; a rule with a high false-positive rate is retuned or removed.

May not: diagnose, recommend or alter a dose, triage to "no action" without human sign-off, or hide its uncertainty. If assistance starts to influence decisions, the applicable software-as-a-medical-device regime must be assessed before release.

Three discrepancy types are first-class: prescribed but not dispensed, dispensed but not taken, changed without a new order. Each is a task for a person. The loop is allowed to be incomplete, but not allowed to lie.

9. Identity and data flow

The app collects no name. A coordinator-issued participant code and a random device ID are the source identity; mapping to a hospital medical-record number happens at the gateway, only with explicit consent, and is recorded in the audit log. A language switch never changes a stored code. Encryption is local first: the network is never the first writer. Sync is optional and off by default. Diet estimates stay out of clinical Observation resources so an estimate never enters a record disguised as a measurement.

10. Governance and safety

  • DPIA before scale. Health data, vulnerable participants and shared devices: document risks and mitigations, not intentions.
  • Named clinical owner. Every rule, flag and escalation has a person accountable for it.
  • Consent and revocation. Timestamped, read aloud in Hindi, revocable by erasing locally; server-side propagation is part of the gateway design.
  • Access review and retention. Role membership reviewed on a schedule; a documented retention and deletion policy.
  • Audit and incident response. Access, exports and decisions logged; a disclosure route and a review cadence.
  • Regulatory posture. v1.0 is not a medical device and makes no diagnostic or treatment claim. Any later assistance that influences a decision triggers a regulatory assessment first.

11. Phased rollout

The order is deliberate: capture, then trust, then share, then act. Each phase has a precondition, so it cannot be announced before it is operable.

PhaseScopePrecondition
0 — ObservationalSmall cohort, no intervention, clinician consent, stop rule for adverse eventsEthics approval and a named physician supervisor
1 — One districtOne clinic, one coordinator, one clinician owner; manual where possibleData-processing agreement, retention policy, gateway live
2 — Several clinicsReconciliation queue, follow-up scheduling, regional food and language packsStaffed review window and weekly operating review
3 — National railsConsent-gated exchange, local residency, per-site adaptersLocal legal basis, data guardians and audited access

No hospital is named as a partner or pilot site in this document. Naming a site before an agreement exists would be a false claim; the design is published so that any site can evaluate it on its merits.

12. What would make this real

Metrics that decide: record completeness per participant-week; time from record to clinician review; medication discrepancies found and resolved; follow-up kept without travel; escalations with a documented outcome; participant-reported trust and burden.

Failure modes to design against: pilot theatre (a dashboard nobody opens), data graveyards (records nobody acts on), consent drift, automation overreach and toolchain fragility. The countermeasures are one clinician-facing artefact that is measured, a queue with ageing, consent receipts and revocation, language rules plus audit, and a scripted dependency-light build.

The honest line: the participant app and the browser demo exist today. Every hospital component here is a design proposal. See the function map for the Shipped / Demo / Roadmap status of each capability, or open the labelled hospital illustration to see the workflow without any real data.
